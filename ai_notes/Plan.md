### Software Implementation Plan: Text‑Only Long‑Term Conversational AI Agent (2025)

This plan translates the research into a concrete, end‑to‑end implementation blueprint. It is written for a junior engineer to execute confidently, providing the rationale behind each choice and clear acceptance criteria. It intentionally avoids code and focuses on outcomes, responsibilities, interfaces, and operational practices.


### 1) Purpose and Scope

The purpose of this system is to deliver a durable, multi‑channel conversational agent that reliably engages users over long time horizons with coherent, contextually grounded interactions. The primary user‑facing capabilities are threefold: first, to broker human introductions using a strict double opt‑in protocol so that both participants explicitly consent before any connection occurs; second, to act as a career coach and reflective partner through periodic nudges, guidance, and goal‑tracking behaviors; and third, to serve as a local guide by recommending nearby events that align with user interests, availability, and consented preferences. The agent must develop and maintain a stable persona that feels consistent and supportive to each user over time while adapting to known preferences and history. This system is not a generic chatbot; it is a tightly governed orchestration of typed inputs and outputs, where deliberate tool calls, audited decisions, and typed contracts make behavior observable, testable, and safe.

The scope of this implementation includes an API layer to receive webhooks and administrative requests, a durable workflow orchestrator to manage long‑running conversations and schedules, an agent runtime that consumes typed context and tools to produce decisions and content, and a data layer that preserves relational truth with semantic recall. The plan prescribes how to normalize messages at ingress, how to enforce security and compliance at boundaries, and how to build a memory architecture that separates ephemeral context from durable summaries and user facts. Included is a comprehensive observability posture that captures structured logs, traces, and metrics with aggressive redaction, and a reliability story that treats retries, backpressure, and cost budgets as first‑class concerns. The plan also defines environments, deployment processes, and operational runbooks so that changes can be shipped safely and incidents can be resolved quickly. Out‑of‑scope items include voice, browser UIs beyond minimal operator utilities, and channel features that do not map to our unified abstraction without explicit adapter‑level documentation and risk acceptance.


### 2) Architectural Overview

The architecture intentionally separates concerns into independently deployable services that communicate through typed interfaces and durable boundaries. The API layer, implemented with FastAPI, receives provider webhooks, validates authenticity, normalizes payloads into a stable domain shape, persists both raw and normalized forms, and publishes signals to the workflow layer. The workflow orchestrator, built on Temporal workers, owns long‑lived conversation state, retries, timers, and schedules; it never performs side effects directly beyond invoking activities that are explicitly idempotent and bounded by timeouts. The agent runtime, implemented with Pydantic AI, acts as the reasoning and planning component that consumes typed inputs, calls strictly typed tools for retrieval and action planning, and returns typed outputs that feed the orchestrator’s next decisions. Tooling is provided via MCP-based toolsets mounted to the agent so discovery, schema, and invocation are standardized across local and remote tools as described in Research.md; this decouples business logic from tool hosting and allows server-side evolution of tools with stable contracts. Durable execution is achieved by integrating Pydantic AI with Temporal directly per Pydantic AI’s Temporal guidance: model requests, tool calls, and MCP server communication execute as Temporal activities, while the deterministic agent run loop executes in a Temporal workflow that coordinates those activities and persists progress for replay. The data layer, using Supabase Postgres with pgvector, stores relational truth such as users, conversations, consents, and message metadata, while embeddings provide semantic recall over summaries and profile cards without persisting raw transcripts in cleartext logs. Observability is pervasive and consistent, with Logfire providing structured logging and tracing augmented by OpenTelemetry for cross‑service stitching.

Data flows begin at the channel edge and immediately cross a durable boundary before any significant logic executes. A provider such as Twilio for SMS or Meta’s WhatsApp posts to a webhook; the API validates the signature or verification token exactly as the provider specifies, rejects invalid requests with a closed‑failure posture, then transforms accepted payloads into a normalized `InboundMessage` shape while preserving the vendor payload in a `raw_vendor` envelope for audit. After writing both forms to storage, the API publishes an event or signals the relevant `ConversationWorkflow` instance with an immutable payload and a correlation identifier that will follow the request through the system. The workflow evaluates state and timing using deterministic logic and calls the agent with bounded context to plan the next action, which might be asking a clarifying question, proposing an introduction plan, scheduling a reminder, or retrieving memories to ground a reply. When a message must be sent, the workflow emits an activity call that creates a provider‑scoped idempotency key, logs a durable intent, and invokes the adapter for the target channel; the adapter maps the normalized `OutboundMessage` to the provider’s API, handles retries with safe deduplication semantics, and records delivery statuses for observability and audits.

The system is designed to degrade gracefully and prove its behavior at the edges. When iMessage is used through a provider such as LoopMessage, the architecture treats the relay as a privileged boundary with heightened security controls, egress restrictions, and health monitoring; a transparent fallback to SMS is activated on explicit failures, timeouts, or health degradation. All services include health and readiness endpoints suitable for rolling deployments, and each service can be scaled independently: the API for webhook concurrency, the orchestrator by Temporal task queue demand, and the agent service by tool workload characteristics and token budgets. The plan favors additive evolution and typed contracts so that changes to tools, events, or workflows are versioned and do not break in‑flight executions. The result is a system that avoids leaky abstractions, keeps the core simple and durable, and confines provider quirks to adapters where they can be managed and tested explicitly.
LoopMessage serves as the initial external channel integration, establishing the first end‑to‑end path before additional channels are added. This prioritization reflects the desired user experience parity with iMessage and ensures that adapter patterns, normalization, and durable orchestration are proven on a rich channel first. The fallback posture remains explicit: if LoopMessage delivery fails or times out, or health checks degrade, the system will route a user‑transparent fallback to SMS (and later WhatsApp where consented), recording the decision and rationale for audit. By making LoopMessage first‑class at inception, the team validates the most complex adapter early while keeping core logic insulated from provider specifics through the normalized contracts and workflow activities described above. Subsequent channel integrations inherit these patterns rather than re‑inventing them.


### 3) Domain Contracts and Data Model (conceptual)

The domain layer defines normalized shapes that decouple business logic from vendor payloads while preserving the fidelity necessary for audits and advanced features. The normalized `InboundMessage` contains a stable identity, a channel identifier, a conversation identifier that maps consistently for each channel’s notion of threads or groups, participant identifiers for sender and recipient where relevant, optional text, a list of media references represented as URLs rather than raw bytes, and a `raw_vendor` dictionary that captures the unmodified source payload. This structure is purposely minimal and stable so that Temporal signals, agent tools, and storage schemas do not need to evolve with each provider change; the preserved `raw_vendor` field is the escape valve for channel‑specific nuance. The normalized `OutboundMessage` contains a precomputed idempotency key that is unique per intended side effect, a target channel, a recipient identifier in the channel’s address space, optional text and media references, and optional delivery preferences such as urgency hints or quiet hours that the adapter can interpret or ignore based on capability. Workflow signal payloads wrap these normalized messages with durable correlation context and any workflow‑relevant metadata so they can be processed deterministically, queried for introspection, and replayed without ambiguity.

Memory is modeled explicitly across working, episodic, semantic, and procedural tiers so that storage and retrieval are predictable and auditable. Working memory exists only within running computations as bounded context windows and is never persisted as a durable store; episodic memory consists of structured summaries of interactions with timestamps, sentiment, and intent annotations that allow the system to answer what happened and when; semantic memory stores durable facts, preferences, entities, and relationships about users and networks; procedural memory encodes policies, playbooks, and guardrails that govern agent behavior and can be reviewed like code and rolled out behind flags. In storage, relational tables capture canonical truth such as users, conversations, consents, introductions, and message metadata, while embeddings are stored for episodic summaries and profile cards rather than raw transcripts to minimize sensitive content replication. Object storage holds media when necessary and is referenced by signed URLs with controlled lifetimes, ensuring that operational logs and traces never carry large or sensitive payloads. Indexing strategies favor composite keys for hot query paths—for example channel and conversation pairs with recency filters—to ensure that operational lookups remain predictable under load.

Data evolution follows additive principles and explicit versioning. New fields are introduced as optional with defaults, schema changes are rolled out with dual‑read or dual‑write periods when necessary, and deprecations are planned with explicit cutovers rather than spontaneous removal. Identities and idempotency are first‑class: every outbound side effect generates a deterministic key stored alongside the durable intent record, enabling safe retries without duplication and preserving exactly‑once‑like semantics at the edges. Events that represent state transitions are written to an event ledger with provenance, which later supports analytics, replays, and audits without reaching into raw transactional tables. The model intentionally separates processing shapes used within workflows and tools from any warehouse or analytics schemas, so that operational evolution does not create churn in analytical pipelines.


### 4) Messaging Channels and Adapter Strategy

Communication with external channels is isolated behind a `MessagingPort` interface so that vendor‑specific logic, schemas, rate limits, and quirks do not leak into core business logic. Each adapter implements two core responsibilities: parsing inbound vendor payloads into normalized `InboundMessage` structures and sending normalized `OutboundMessage` structures to the vendor API with the correct authentication, headers, idempotency semantics, and error handling. The Twilio adapter validates webhook signatures using the provider’s header and the exact URL and form payload as specified, rejects invalid requests with a 403 without revealing sensitive details, decodes `application/x-www-form-urlencoded` forms, and maps fields such as sender, body, and media into the normalized event. The WhatsApp adapter handles both the challenge verification handshake on GET and inbound messages on POST, enforces the 24‑hour customer care window for free‑form messages, and ensures that template messages sent outside the window adhere to registered content and locale variants; it also records quality signals and provider error codes to inform routing decisions and observability. The iMessage adapter, if used via a provider like LoopMessage, treats the provider as a high‑sensitivity boundary by restricting egress, rotating credentials aggressively, redacting payloads in logs, and incorporating health checks; when health degrades or sends time out or fail, the adapter transparently engages a fallback policy to SMS or WhatsApp according to the user’s consented preferences.

Inbound parsing is treated as a contract that must not drift silently. Vendor DTOs are defined near the adapter and kept versioned; contract tests use provider sample payloads to validate both acceptance and rejection paths including signature failures and malformed inputs, ensuring that upgrades to provider SDKs or unseen payload variants do not leak into production behavior. Every inbound request is assigned a durable correlation identifier that is stored alongside the normalized event and propagated through workflows and agent calls, enabling cross‑cutting traces and forensic reconstruction during incidents. When providers introduce new event types—for example reactions or read receipts—the adapter evolves first, and the normalized model either expands additively or leaves the new detail inside `raw_vendor` if it does not map cleanly; downstream business logic only changes when the new capability is explicitly adopted. This separation keeps the system adaptable without destabilizing core processing.


### 5) API Surface and Webhook Ingress

The API layer exists to secure the boundary, validate inputs, normalize them, persist the results, and delegate to durable processing without performing heavy business logic inline. Each webhook route implements provider‑specific authentication exactly as documented, and any mismatch results in an immediate 403 without disclosing whether the token or signature format was incorrect, thereby reducing information leakage. Inputs are bounded with explicit size limits, and rate limiting or bot protection mechanisms are applied to blunt automated abuse; failures inside the handler are logged with redacted context and correlation identifiers, but the response avoids propagating sensitive details to the caller. After validation and normalization, the handler persists both the `raw_vendor` payload and the normalized `InboundMessage` into durable storage and acknowledges receipt quickly, deferring all additional work to background tasks or Temporal signals so that provider timeouts do not impact correctness. Health and readiness endpoints are provided separately, remain side‑effect free, and are suitable for liveness checks and rolling deployments.
For LoopMessage ingress specifically, the webhook handler verifies the `Authorization: Bearer <token>` header and any provider‑specific secret header, compares against stored credentials, and denies mismatches without revealing which check failed. The handler accepts JSON payloads that include event types such as `message_created`, `message_delivered`, `message_read`, `typing_started`, `typing_stopped`, `reaction_added`, `participant_joined`, `participant_left`, and `thread_started`, and it normalizes these to domain events while storing the full payload in `raw_vendor`. The handler enforces tight timeouts and responds quickly with a minimal acknowledgment so the provider is not held hostage to internal processing; heavy work is signaled to Temporal immediately. Sandbox and replay routes are documented for local development so engineers can post recorded LoopMessage payloads to exercise parsing and normalization without relying on live events. These practices make the LoopMessage path the reference implementation for all future channel webhooks.

Administrative endpoints are minimized and strictly controlled with role‑based access and audit logging because they can impact live workflows and user experiences. Where an operator must trigger replays, resends, or cohort actions, those actions are mediated by durable workflows or queues rather than executing heavy side effects inside the HTTP handler, ensuring that retries, time budgets, and observability are consistent with the rest of the platform. Documentation for adding a new webhook is explicit: create a route under the appropriate router, implement provider validation faithfully, define or update the vendor DTO near the adapter, add normalization to the stable `InboundMessage` without altering its semantics, ensure both raw and normalized forms are persisted, emit a Temporal signal with correlation context, and write contract tests for both acceptance and rejection cases. The API avoids storing raw message bodies in logs; redaction and hashing of identifiers are enforced at ingress to prevent accidental leakage. This disciplined edge posture allows the interior to remain simple and deterministic.


### 6) Orchestration with Temporal

Temporal provides durable execution for long‑lived, eventful processes and is the backbone of conversation state, retries, timers, and schedules. The `ConversationWorkflow` is scoped per user or per conversation, chosen according to how provider identifiers map to durable identities and the expected concurrency of simultaneous threads. Workflows are strictly deterministic: they do not reach for system time or random sources outside Temporal APIs, and any changes in logic go through versioning gates so that in‑flight executions continue safely while new executions adopt the updated behavior. External side effects such as sending messages, writing to storage, or calling third‑party services are performed in activities that have explicit timeouts, retry policies with exponential backoff, and idempotency semantics based on precomputed keys stored with durable intent records. Signals deliver inbound messages into the correct workflow instance, and queries expose read‑only state such as a summary for operator dashboards without mutating execution. In the agent path, Pydantic AI integrates with Temporal so that model requests, function tool calls, and MCP server communication run as activities while the agent run loop executes in the workflow, ensuring replay safety and aligning with the durable execution model documented by Pydantic AI.

Workflows encode the narrative of the conversation with guardrails that make behavior predictable. A common pattern is to receive a signal for an inbound message, update internal state if necessary, decide whether to request more information, retrieve relevant memories, propose an introduction plan, or schedule a follow‑up nudge at a later time; each decision is recorded in observability fields for later analysis. Where multi‑step actions occur—such as obtaining consent from two parties before brokering an introduction—the workflow orchestrates a SAGA pattern with compensating actions so that partial progress can be safely undone if a later step fails. Timers are used to implement reminders and pacing, and schedules are used to trigger periodic work such as weekly summaries or event digests; these are observable and controllable from the Temporal UI with search attributes such as user identifier, channel, locale, and high‑level conversation state. Acceptance is demonstrated when a worker restart or deployment does not cause duplicated sends, when retries honor idempotency, and when operator queries can reliably introspect live workflow state without race conditions.

Adding new behavior follows a specific sequence that reduces risk. First, design the desired action as an activity with clear inputs and outputs and define the idempotency strategy; second, add workflow logic that calls the activity within version gates and records decisions for observability; third, if the behavior involves the agent, register a Pydantic AI tool or MCP toolset with stable IDs and names (required for Temporal activity identity) and configure activity timeouts and retry policies per tool; fourth, write contract tests that simulate signals, timers, and failure modes including timeouts, provider throttling, and model/tool retries; fifth, roll the change out behind a flag or cohort guard if risk warrants; and finally, monitor Temporal and Logfire metrics and traces to confirm that tail latencies and error rates remain within SLOs. This disciplined approach preserves the benefits of durable execution and ensures that business logic evolves without compromising determinism or safety.


### 7) Agent Runtime with Pydantic AI

The agent is a typed reasoning engine that consumes structured inputs, invokes typed tools, and returns structured outputs under strict budgets and policies. Prompts encode persona, tone, and high‑level governance, but operations occur through tools whose inputs and outputs are expressed as Pydantic models with explicit validation; this keeps failures visible at the boundary with clear error messages tied to specific fields or constraints. Tools are grouped by capability: retrieval tools fetch user profiles, episodic summaries, events, or network candidates; action tools produce send intents, schedule follow‑ups, or create introduction plans that the workflow can enact; memory tools upsert summaries and facts with provenance and timestamps; moderation tools evaluate content and escalate when policies are ambiguous or violated. MCP-based toolsets are the default integration mechanism so the agent can mount local toolsets and remote MCP servers with the same discovery and invocation contract; toolset IDs and agent names are kept stable to match Temporal’s durable activity identity requirements as documented by Pydantic AI. Every tool call is wrapped in a span that records latency, token usage, payload sizes with redaction, and outcomes so that costs and performance are tracked rigorously. Concurrency is managed so that asynchronous tools run on the event loop and synchronous tools are offloaded to bounded thread pools, avoiding resource starvation.

Governance and budgets are enforced at the agent layer. Token budgets per request prevent runaway costs, and per‑tool invocation limits ensure that a single capability cannot dominate computation or degrade user‑visible latency. When a model proposes multiple tool calls in a single turn, the runtime schedules them concurrently while respecting concurrency caps and rate limits; results are combined deterministically to avoid non‑reproducible ordering effects. MCP is adopted universally for external tools so catalogs can evolve independently while remaining type‑checked and observable; toolsets expose JSON Schema and carry stable IDs, and activities are configured with explicit timeouts and retry policies per tool per Temporal guidance. When adding a new tool or toolset, engineers define the input and output models with clear field constraints, document versioning and deprecation strategies, register the tool with the agent and assign a stable toolset ID, and add dataset‑driven tests that verify both happy paths and constraint violations; in production, tool metrics are monitored for shifts in latency, error rates, and cost.

Persona discipline and memory usage are aligned. The agent’s voice remains consistent and humane, adapting terseness or enthusiasm per user preferences while remaining transparent about limitations and uncertainties; retrieval policies require grounded citations when claims rely on memory or external context. Working memory windows are intentionally small and curated, and episodic memory updates trigger embeddings for semantic recall while avoiding duplication of raw content in operational logs. When the agent prepares an introduction plan, it must produce messages for each party that clearly describe the topic and request consent without disclosing sensitive details prematurely, and it must include enough context that a user can confidently accept or decline. These requirements are encoded as typed outputs that the workflow can verify before proceeding, making consent both a behavioral and a technical contract.


### 8) Memory and Data Layer (Supabase: Postgres + pgvector)

The data layer balances relational truth with semantic recall in a single operational envelope to reduce complexity and improve reliability. Core relational tables store users with stable identifiers that span channels, conversations with composite keys that capture channel and conversation identifiers, message metadata without raw bodies, consents with timestamps and scopes, introductions with state transitions and compensation notes, and optional catalogs such as events if the product integrates structured sources. An embeddings table stores vectors for episodic summaries and profile cards along with metadata fields such as user identifier, topic, recency, and provenance; indexes such as HNSW or IVF are selected based on corpus size and latency goals, and queries use metadata filters first before ranking by vector similarity to create hybrid search. Triggers keep embeddings current when summarized notes are written or updated, and outbox triggers pair intent writes with asynchronous dispatch when the design calls for database‑driven sends. Object storage keeps media out of hot operational paths and provides signed URLs with controlled lifetimes so that attachments remain accessible without creating long‑lived exposure.

Security and access are enforced at the storage boundary. In production, Row Level Security adopts a default‑deny posture with explicit policies per tenant or user, and only trusted server processes use a service role key; development and staging environments maintain similar scoping to prevent accidental reliance on broad privileges. Schema evolution uses migrations that run in CI and before deploys, and rollbacks are documented and tested so that failed deploys do not strand incompatible schema states. Backups with point‑in‑time recovery are scheduled and disaster recovery exercises are conducted on a regular cadence to verify that restores work as expected and that recovery time objectives are met. Retention policies implement progressive summarization, time‑decay for low‑signal content, and pinning for high‑value facts such as consents or commitments with explicit TTLs and renewal logic; these policies are visible to operators and reviewed periodically for alignment with product and compliance goals.


### 9) Context Engineering and Retrieval

Context is treated as a product with budgets and guarantees rather than an afterthought. Ingestion pipelines standardize sources into a snippet schema with fields for title, body, source, last updated, and attribution so that prompts can treat heterogeneous content uniformly; chunking strategies respect semantic boundaries rather than arbitrary fixed lengths, improving retrieval quality and grounding. Query planning begins with intent classification into categories such as answering a question, planning a sequence, recommending content, or brokering an introduction, and retrieval strategies adjust accordingly—for example, introductions rely on a mix of semantic similarity and structured constraints such as geography, skills, and recency. Results are assembled into a context package that includes concise, high‑signal excerpts with citations and avoids redundant or stale content; diversity‑promoting techniques such as maximal marginal relevance or lightweight re‑ranking can be applied when corpora are heterogeneous or dense. Budgets for tokens and latency are explicit, and the system degrades gracefully by pruning low‑utility snippets first or staging retrieval in waves that trade latency for quality only when the user remains engaged.

Evaluation happens both offline and online to keep the retrieval system honest. Offline suites measure recall at K for relevant facts, citation accuracy, and leakage of disallowed content such as PII or sensitive secrets; datasets are updated over time to reflect drift in user behavior and content sources. Online metrics track perceived helpfulness, latency percentiles, introduction acceptance rates, and costs; changes to retrieval parameters are rolled out behind flags and can be rolled back automatically if error rates or latency tails breach thresholds. Grounding is required for factual claims: whenever the agent uses retrieved content to support an assertion or recommendation, it includes a citation with enough metadata that an operator can trace it back to the source. This discipline creates a feedback loop where retrieval quality improvements show up in user‑visible outcomes rather than just offline scores.


### 10) Observability (Logfire + OTel)

Observability is designed in from the start so that incidents can be diagnosed in minutes rather than hours. Structured logging via Logfire ensures that every record carries durable correlation fields such as request identifiers, conversation identifiers, workflow identifiers, and message identifiers; sensitive bodies and PII are redacted or hashed so that logs cannot become a shadow data store. Tracing is consistent across services, with spans created at webhooks, normalization points, workflow transitions, agent tool calls, and provider sends; OpenTelemetry exporters allow traces to be forwarded to a preferred APM while maintaining a single model for instrumentation. For Temporal + Pydantic AI integration, the Temporal client is configured with the Logfire plugin so that workflow and activity telemetry as well as agent model requests and tool calls are exported consistently, aligning with Pydantic AI’s durable execution observability guidance. Metrics capture latency percentiles, error rates, throughput, provider delivery statuses, and token and cost budgets; SLOs are defined around user‑perceived quality such as webhook latency, workflow success rates, tool call success rates, and channel delivery success, and alerting is based on error budgets rather than raw counters to reduce noise. Dashboards present end‑to‑end narratives that connect a webhook through normalization, workflow decisions, agent tools, and provider outcomes so that an on‑call engineer can see exactly where time and errors are spent.

Instrumentation practices are standardized so that teams do not have to rediscover them. Each service includes initialization that configures Logfire with the service name, deployment environment, and version, and wraps the web framework or agent runtime to capture common spans automatically. Outbound HTTP clients are centralized with strict defaults for timeouts, retries, and TLS validation so that external calls cannot silently hang or bypass certificate checks. Redaction policies are implemented at ingress to scrub message bodies and PII fields across logs and traces, and periodic audits verify that no sensitive content has slipped through. Operators can correlate events across services using the same identifiers, and incident playbooks reference these dashboards and trace views explicitly.


### 11) Security

Security begins with threat modeling and is enforced at boundaries with concrete, testable controls. The team enumerates actors such as end users, operators, MCP servers, and third‑party providers, and assets such as PII, credentials, embeddings, transcripts, and consents; data flows are mapped to identify trust boundaries at public webhooks, provider callbacks, MCP connections, and database access. Access control follows least privilege, separating human and machine identities and using short‑lived credentials or workload identity when possible; administrative endpoints and dashboards are protected by role‑based access control and destructive actions are gated behind break‑glass procedures with audit trails. Secrets are managed in a vault rather than source control or plaintext files, are rotated routinely and after incidents, and are scoped with minimal privileges; for high‑sensitivity environments, hardware‑backed keys are preferred. Input validation and sanitization are applied at all boundaries, static and dynamic analysis run in CI, and dependencies are pinned and scanned; outbound HTTP clients enforce strict timeouts, retries, and certificate validation so that supply chain or network failures cannot escalate into broader compromises.

Webhook boundaries are given special attention because they face the public internet and third‑party providers. Twilio signatures are validated using the official algorithm against the exact URL and form payload; any change in the route or parameters is reflected in configuration and tests so that validation remains correct. WhatsApp verification tokens are checked for subscription challenge handshakes and inbound requests, and the system rejects invalid requests without disclosing specifics. For iMessage via a provider, the relay host is treated as a privileged boundary with restricted console and logging access, and egress to the provider is tightly controlled and monitored with heartbeats so that traffic can be drained to SMS automatically if health degrades. These measures ensure that the system fails closed and that any bypass attempts are visible in observability pipelines.


### 12) Compliance

Compliance aligns the system with legal and platform rules and must be encoded as system behavior rather than tribal knowledge. The team maps data flows to applicable regimes such as GDPR for EU data subjects and CCPA/CPRA in California, determines what is in scope and why, and documents these decisions alongside retention policies and access controls. Messaging rules are implemented concretely: A2P 10DLC registration for SMS in the United States is completed and reflected in number provisioning and sender IDs, STOP and HELP flows work reliably even under partial system failure, and WhatsApp’s 24‑hour customer care window and template categories are enforced at the adapter level so that violations cannot occur. Data subject access requests are supported with mechanisms to export, correct, and delete user data across relational tables, summaries, and embeddings; provenance is tracked so that reconstructed histories remain truthful without exposing raw sensitive content improperly. Audit trails cover admin access, schema changes, and reads of sensitive data, and internal audits are scheduled with findings tracked to remediation with owners and deadlines.

Compliance work is integrated into CI/CD so that violations block releases rather than surfacing after deployment. Policies are versioned, linked to code that enforces them, and validated by contract tests where possible—for example, STOP and HELP flows are exercised automatically in test environments, and WhatsApp template enforcement rejects unregistered content. Encryption is enforced in transit and at rest, with distinct keys per environment and per data class where appropriate; envelope encryption and field‑level encryption are adopted for particularly sensitive fields. Training and awareness programs ensure that engineers and operators handle PII correctly and recognize phishing or social engineering attempts; tabletop exercises rehearse incident response so that the organization can execute under pressure. These practices ground compliance in everyday engineering rather than treating it as an afterthought.


### 13) Reliability and Resilience

Reliability is engineered through redundancy, isolation, and disciplined change management; it is not left to chance. Side effects such as messaging are protected by outbox and inbox patterns with idempotency keys so that at‑least‑once delivery with idempotent consumers approximates exactly‑once semantics at the edges; retries are explicit, backoffs exponential, and dead‑letter queues isolate poison messages. Circuit breakers and bulkheads prevent a failing provider from consuming all resources: adapters run in their own bounded thread pools or async concurrency limits, and failures trip breakers that trigger fallbacks where policies allow. Backpressure is monitored through queue depths and latency percentiles, and autoscaling policies are defined per service with sensible floors and ceilings to avoid thrash; API replicas are run in multiples, and worker concurrency is tuned to the slowest downstream. Cost is treated as a reliability risk: token budgets for agents, rate limits for vector queries, and messaging spend are tracked by feature and tenant, and throttles are activated if costs spike abnormally to prevent runaway bills that could degrade service.

Resilience is validated through regular game days and chaos experiments. The team intentionally fails adapters, revokes credentials, and restarts Temporal workers mid‑run to confirm that durable execution and fallbacks behave as designed and that no duplicate sends occur; drills include WhatsApp template blocks, carrier throttling, and iMessage relay downtime where applicable. Runbooks are validated during these exercises and updated when gaps are found; dashboards are used to verify detection and diagnosis paths with correlation identifiers. Disaster recovery is practiced by restoring from backups into staging environments and running smoke tests that cover critical flows, ensuring that recovery procedures remain fresh and verifiable. This systematic approach makes incidents bounded and predictable rather than surprising.


### 14) Testing Strategy

Testing spans unit, contract, integration, end‑to‑end, performance, security, and resilience so that the system’s promises are verified under realistic conditions. Unit tests cover the smallest pieces of logic including tool functions, normalization routines, and deterministic workflow branches; Pydantic validation errors are asserted directly so that mis‑shapen data cannot slip through unnoticed. Contract tests encircle adapter boundaries and webhooks: signature validation is tested with both correct and incorrect inputs, provider sample payloads are replayed locally, and normalized events are compared against golden fixtures to catch regressions. Integration and end‑to‑end tests run the full path from ingress to orchestrator to agent to outbound activity and adapter with simulated provider responses, including failure modes such as HTTP 429s, timeouts, or invalid WhatsApp templates, and then assert that retries, idempotency, and fallbacks produce safe and observable outcomes. Performance testing uses realistic concurrency and payload sizes to measure p50, p95, and p99 latencies, identify saturation points such as thread pools or database connections, and confirm that autoscaling policies keep the system within SLOs.

Security and resilience testing complement functional checks. Static analysis and software composition analysis run in CI; dynamic application security testing exercises running systems for common vulnerabilities; fuzzing targets webhook parsers and adapter boundaries to uncover parsing edge cases. Chaos tests simulate provider outages and partial network failures to validate circuit breakers, backpressure handling, and graceful degradation; snapshot tests capture prompt and tool outputs so that prompt engineering does not drift silently across releases. Test data management is explicit, with synthetic datasets and recorded fixtures used in CI to avoid dependence on live vendor systems; developers have harnesses that replay recorded webhooks and provider responses locally to accelerate iteration without external dependencies. These practices ensure that correctness is verified continuously and economically.


### 15) Deployment and Environments (Railway)

Deployment is organized around a multi‑service Railway project that separates the API, orchestrator, and agent processes so that each can scale and be deployed independently. Container builds are deterministic, pinning Python and base OS versions and using multi‑stage builds to keep images small; environment variables are configured per service and per environment using Railway’s secret management, and no secrets are committed to source control. Environments follow a promotion path from development to preview to staging to production; pull requests deploy automatically to preview with outbound callbacks to vendors disabled, staging mirrors production traffic patterns with feature flags as needed, and production accepts only signed images that have passed load tests and compliance gates. Database migrations run as explicit jobs before application deploys to keep schema evolution synchronized with code; rollbacks are documented and tested so that deployments can be reversed without data loss. Scaling rules are defined per service, with a minimum of two API replicas for availability, Temporal worker counts sized to task queues, and agent service concurrency tuned to token budgets and tool latencies.

Operational safeguards are applied at the platform level. Health and readiness probes gate traffic during rollouts to prevent cold starts or partial initialization from causing user‑visible errors; graceful timeouts and termination hooks allow in‑flight requests to complete during redeployments. Network policies restrict egress where sensitive providers are involved, such as iMessage relays; TLS is enforced for all service‑to‑service communication and external calls, and certificates are rotated routinely. Logs, metrics, and traces are exported centrally so that operators can correlate behaviors across environments and services; environment‑scoped keys and explicit configuration prevent cross‑contamination. These practices make deployments routine rather than risky.


### 16) Operations, Runbooks, and SLOs

Operations are governed by documented runbooks, explicit SLOs, and a culture of continuous improvement. Runbooks cover provider outages where fallbacks must be activated and user messaging updated, credential compromise where keys must be revoked and rotated quickly, draining an adapter safely when a bug is discovered, rolling back a schema change that has degraded performance, and incident triage using correlation identifiers to trace a request end‑to‑end. Each runbook names an owner, defines prerequisites, describes ordered steps with expected outcomes, and includes verification checks that confirm recovery; after every incident or drill, the runbook is updated to reflect lessons learned. SLOs align with user experience: webhook p95 latency within a defined threshold, workflow step success rate above a target, agent tool call success rates and costs within budget, and provider delivery success rates by channel; alerts are configured on burn rates so that the team responds when user impact is likely rather than when counters blip. On‑call rotations are staffed with clear escalation paths, and dashboards referenced by runbooks are kept current and visible.

Continuous improvement is institutionalized through postmortems and change management. After incidents, the team conducts blameless postmortems that capture detection, diagnosis, and prevention actions, and it tracks those actions to completion; changes with risk are rolled out gradually behind flags or to small cohorts and monitored closely. Operators periodically review cost dashboards to ensure that token usage, vector queries, and messaging spend remain efficient and predictable; where hot paths are identified, the team implements caching, batching, or index improvements. These practices keep operations predictable and improve reliability without slowing delivery.


### 17) Project Layout and Developer Experience

The repository is structured to reflect the architecture and promote clarity for new contributors. Routers separate webhook ingress, health/readiness, and administrative endpoints so that transport concerns do not leak into business logic; adapters live in their own area with vendor DTOs and tests close by; the agent runtime and its tools are isolated with explicit type definitions; and common domain types and protocol models live in a central module that other services depend upon. Coding standards emphasize descriptive naming, explicit typing, and early returns to reduce nesting; formatting, linting, and type checking are automated so that diffs remain focused on substance. Local development is standardized using uv for environment and dependency management, with make‑like commands or scripts to run the API with reloading, launch Temporal workers, start the agent service, seed the database, and replay recorded webhooks without hitting real providers. Documentation includes architecture decision records that capture trade‑offs, onboarding guides that bring a new engineer to productivity in under a day, and contribution guidelines that set expectations for tests and observability.

Developers have the tools to debug and iterate quickly without risking production systems. Mock adapters allow testing end‑to‑end flows locally, and fixtures reproduce provider payloads and responses faithfully. Golden traces capture expected behavior for common flows and can be replayed to detect regressions in prompts or tool behavior; snapshot tests guard against accidental changes in agent outputs. The result is a developer experience that prioritizes clarity, safety, and speed.


### 18) Phased Implementation Plan

Implementation proceeds in phases that each produce a durable, observable increment of value while reducing risk through isolation and clear acceptance. Foundations come first: the team bootstraps the repository, configures uv environments, pins dependencies, and initializes FastAPI with health endpoints; Logfire is configured with service names, environments, and versions and instruments FastAPI and the agent runtime; outbound HTTP clients are centralized with strict defaults; and a basic normalization layer is defined with types for `InboundMessage` and `OutboundMessage`. Acceptance at this phase is demonstrated when health endpoints respond consistently, structured logs include correlation identifiers without raw content, initial traces are visible end‑to‑end for synthetic calls, and CI runs format, lint, and type checks automatically and successfully.

The first channel integration targets iMessage via LoopMessage so that the richest event surface is proven early. The webhook is implemented with bearer token and secret verification as provided by LoopMessage, normalized events are stored alongside raw payloads, and a minimal workflow echoes a response through the LoopMessage adapter using a precomputed idempotency key while honoring thread and group identifiers for continuity; provider delivery and read receipts are recorded and tied back to the durable send intent and correlation identifiers. Contract tests cover acceptance and rejection paths including invalid authorization headers, unknown event types, and missing thread metadata; idempotency is verified by replaying sends and confirming no duplicates are created downstream even when provider retries occur. Acceptance is achieved when a staged environment can receive and respond to LoopMessage events reliably, when reactions and typing indicators are parsed without breaking normalization, and when observability shows the complete narrative from ingress to delivery with appropriate redaction. Fallback behavior to SMS is validated by simulating provider timeouts or health degradation signals and asserting a single, transparent user message with audit records that explain the decision.
After LoopMessage is stable, the next channel integration adds SMS via Twilio to establish broad reach and serve as the default fallback path. The webhook is implemented with exact signature validation against the full URL and form payload, normalized events are stored alongside raw payloads, and the existing workflow sends responses through the Twilio adapter using precomputed idempotency keys; provider delivery callbacks are recorded and tied back to the durable send intent and correlation identifiers. Contract tests cover acceptance and rejection paths and ensure normalization parity with LoopMessage where semantics overlap; idempotency is verified by replaying sends and confirming no duplicates are created downstream. Acceptance is achieved when the staging environment reliably receives and responds to SMS messages and when fallback transitions between LoopMessage and Twilio are user‑transparent and auditable.

Temporal orchestration follows to introduce durable workflows, retries, timers, and schedules. A `ConversationWorkflow` is created and receives signals for inbound messages; it decides whether to ask a clarifying question or to schedule a follow‑up using timers; activities are used for all external calls with explicit timeouts and idempotency keys. Search attributes are added to make filtering by user and conversation straightforward in the Temporal UI, and a weekly nudge schedule is created as a proof of scheduling. Acceptance requires that restarting workers or redeploying does not cause duplicated sends, that retries happen with backoff rather than bursts, and that operators can query workflow summaries without mutating state.

The agent service is then introduced with a small set of typed tools for retrieval, send intents, and memory updates backed by relational storage, delivered as MCP toolsets with stable IDs and discovery schemas. Persona guidance is added, and the agent is called by the workflow using Pydantic AI’s Temporal integration so the agent run loop executes in a workflow and all model requests and tool calls run as activities with explicit timeouts and retry policies; moderation tools are wired to block unsafe outputs and require escalation in ambiguous cases. Observability verifies per‑tool and per‑activity spans, token usage, and latencies, and budgets are enforced so that the agent’s costs cannot spike unexpectedly. Acceptance occurs when the agent’s outputs are validated by Pydantic models, memory updates create episodic summaries with provenance, MCP tool discovery and invocation behave deterministically with stable toolset IDs, and end‑to‑end flows include agent decisions without degrading latency beyond budget.

Semantic recall is added next by enabling pgvector and storing embeddings for episodic summaries and profile cards. Retrieval pipelines are built to combine metadata filters with vector similarity to produce compact, high‑signal contexts with explicit citations; parameters are tuned offline with datasets that measure recall and citation accuracy and are rolled out behind flags. Acceptance is achieved when retrieval improves helpfulness in online metrics without causing cost or latency regressions, and when citations allow operators to trace claims to sources reliably. Subsequent phases add WhatsApp with verification and template enforcement and track session windows, then implement the introductions feature with double opt‑in and SAGA compensations, and finally integrate iMessage via a provider with strict security posture and progressive fallbacks to SMS. Each phase concludes with drills and audits to validate behavior under failure modes and to update runbooks where necessary.


### 19) Risk Register and Mitigations

The most salient risks are addressed with explicit mitigations. iMessage remains brittle because there is no public, general‑purpose server API; when used through a provider, the host is treated as a privileged boundary with hardened posture, limited egress, and aggressive monitoring, and the system transparently falls back to SMS with user disclosure when delivery fails or health degrades. Providers impose throttles and may filter or delay content; the system respects rate limits, monitors error codes, and routes around failing paths when possible while maintaining a durable ledger for audit and analysis. Workflow nondeterminism could compromise durable execution; the design keeps randomness and time access within activities, uses version gates for changes, and requires contract tests that replay workflows deterministically. Data sensitivity is inherent to messaging; redaction and tokenization are enforced at ingress and across observability, hot operational paths are separated from cold storage, and access is governed by granular policies. Cost spikes can destabilize operations; token, vector, and messaging budgets are monitored and enforced by feature and tenant, and throttles protect the system when anomalies occur.


### 20) Acceptance Checklists (Go/No‑Go)

Before promotion at each major gate—pilot, beta, and production—the system must satisfy narrative acceptance criteria across security, compliance, reliability, observability, and product outcomes. On the security axis, acceptance means every webhook rejects invalid signatures or verification tokens unambiguously with a closed‑failure policy, all secrets are stored in a vault and have been rotated as part of the release, administrative endpoints are protected by RBAC with audit logs showing controlled access, and third‑party security scans or penetration tests have no outstanding critical or high findings. On the compliance axis, acceptance requires that STOP and HELP flows function reliably even when downstream services are impaired, WhatsApp’s 24‑hour care window and template categories are enforced by the adapter without operator intervention, data subject access requests for export and deletion are executed against live staging data successfully, and audit logs immutably record access to sensitive data with timestamps, actors, and purposes. On the reliability axis, acceptance is demonstrated when simulated provider incidents trigger automatic fallbacks without duplicate sends, idempotency keys prevent double delivery under retries and replays, circuit breakers isolate failing adapters without starving the rest of the system, and documented disaster recovery drills complete within the agreed recovery time objectives. On the observability axis, acceptance requires end‑to‑end traces from webhook through workflow and agent to provider send with consistent correlation identifiers, verified redaction of message bodies and PII in logs and traces, live SLO dashboards that an on‑call engineer can use to diagnose issues in minutes, and alerts configured on error budget burn rates rather than raw counters to reduce noise. On the product axis, acceptance is achieved when double opt‑in introductions operate to completion with auditable consent for both parties, coaching nudges and reminders are delivered at the correct cadence with durable timers, and local guide suggestions are grounded with citations that operators can follow back to sources, yielding behavior indistinguishable from a manually curated experience. For the initial LoopMessage‑first rollout, the acceptance dossier additionally demonstrates correct parsing and normalization of LoopMessage‑specific events including reactions, typing indicators, delivery and read receipts, and thread/group identifiers that preserve continuity across replies. Traces show fallback activation from LoopMessage to SMS under simulated provider timeouts or degraded health, resulting in a single user‑visible message without duplication and with durable audit records that explain the fallback rationale. Operators prove that revoking or rotating LoopMessage credentials results in immediate denial at the webhook with closed‑failure behavior and that health checks drain traffic automatically to fallback channels according to policy. Staging load tests show that LoopMessage webhook handling and adapter sends sustain target throughput and latency percentiles with token and cost budgets respected. These additional checks ensure the richest channel behaves predictably and safely before broader rollouts.

Each gate review compiles a short, human‑readable dossier referencing concrete evidence rather than assertions. The dossier includes links to traces for representative end‑to‑end flows, screenshots or exports of SLO dashboards during controlled load, copies of audit logs for sensitive actions taken during testing, and artifact hashes and image digests proving that the versions tested are identical to those slated for promotion. Where risk exists due to known limitations or deferred work, the dossier explicitly documents mitigations and rollback plans with triggers and owners so that promotion remains a conscious, reversible decision. If any acceptance dimension is not satisfied, the promotion is blocked and a single responsible owner is assigned to remediate with a target date and clearly defined re‑test steps. This ritual ensures that the system’s behavior at launch is predictable, governed, and aligned with user trust.


### 21) Working Agreements

The team commits to additive evolution as the default, introducing new fields and capabilities in backward‑compatible ways and reserving breaking changes for rare, well‑justified situations that include explicit versioning, dual‑read or dual‑write periods, and documented cutovers. Typed boundaries are non‑negotiable: vendor DTOs remain confined to adapters, normalization happens at ingress, and domain models and tool interfaces use strict types so that failures are visible and testable at compile time and during validation rather than at runtime in production. No feature is exposed to real traffic without tests that prove correctness under both happy and unhappy paths; specifically, adapter contract tests cover provider signature verification and payload normalization, workflow tests cover deterministic behavior across version gates and retries, and agent tool tests cover validation errors and budget enforcement, all running in CI on every change. Operational discipline is a shared responsibility: incident playbooks are treated as living documents, game days are scheduled and executed to practice fallbacks and recovery, and blameless postmortems result in concrete prevention actions that are tracked to completion and verified. Documentation is treated as part of the deliverable—architecture decision records accompany significant choices, onboarding guides keep ramp‑up time under a day, and contribution guidelines enforce observability, testing, and security hygiene so that velocity is sustained without eroding reliability.


This plan is intentionally explicit about responsibilities, reasoning, and acceptance criteria so that each phase can be executed independently and safely. It is the single source of truth for implementation choices; deviations should be recorded as decision logs with rationale and impact assessments.
